# Match a file with the catalog

For an update when the keys of the file are not exact, the source is a PDF or a messy Excel, there are several files, or a second supplier. These rules hold for any kind of goods. The snapshot of the catalog (get_catalog_snapshot) gives a short version in "guide"; this is the whole method.

1. Read the whole source (every sheet, every page). Make one table: a row is a future product. Leave out the titles of sections, the totals, the empty rows and columns; a title above a group is the section of the rows under it. A cell with several properties written together (a model, a size, a color) goes to several columns. Keep one row per product variant (size, color, version), with its own name. Join multiple files by a shared identifier, never by row order. Resolve ambiguous joins before taking values from them.
2. Tell the user how you understood the columns ("Item No. is the supplier article, Net dealer price is the purchase price") and the rules they gave. A column that was renamed since the last load and has the same data is the same column: use the column of the catalog, never make a new one.
3. Match the rows with this snapshot with a script on the CSV, not by reading it in the chat. A matching key creates a group of candidates, not a final pair. The snapshot has the names of the columns, not their roles: read the roles with get_catalog (role vendorCode is the code of the product, name — the name, description and longDescription — the texts). Find candidates by the exact code; the same code without case, spaces, dashes and look-alike Cyrillic and Latin letters; then the name, the texts and other common columns.
   - For every candidate compare all shared non-empty data from the file and catalog, including explicit facts in the name and texts. Do not compare the value being updated. A missing value is unknown, not a match or a contradiction. Any contradiction makes the pair doubtful. Do not assume that any kind of difference is irrelevant; only the user can say that it does not change the imported value.
   - Accept a pair without a question only when one exact candidate remains, the source key is not repeated, and no data contradicts the pair. Ask if several candidates remain, even if they look identical.
   - Several products of the catalog may take the value of one row only if they differ by an attribute that the file does not state and the user said that this attribute does not change the value; otherwise ask, once for an attribute and not for each product.
   - When several rows of the file have the same key, the key does not choose the row: compare every attribute that each row states with each product, and propose the row that fits each product and ask the user to confirm the choice.
   - If no existing catalog key can target only the approved products, skip the affected rows and explain why. You can offer a separate task to add and fill a unique key (create_field). Do not do that without the user agreeing to the separate change.
4. Ask about likeness, contradictory data, several candidates and repeated source keys. Show the source row, candidate products, the matching and differing attributes, and the current and proposed values. Group cases only when the same decision applies. The user can confirm the pair or ask to skip it. Report an explicit skip without asking again. Use a threshold ("show me everything below 90%") only when the user named it; a percent is your estimate, not a measure.
5. Before preview_import tell the user in simple words: which products change and from what to what (all of them for a short file, examples for a long one); how many rows matched by the exact key, by likeness (confirmed, not confirmed), how many are new, how many are skipped and why, the duplicates inside the file, the products of the catalog that are not in the file; and the problems of the file with an offer ("rows 384–400 have no currency, the others look like USD: apply USD?"), never an error text. Give the user the CSV of the pairs (the row of the file, the product, how it was matched, what was decided, and the number of the question: the same for the products of one question). The same numbers go to matchReport of preview_import, counted in rows of the file of the user: its fields say how. Also list every row used for several products and every key repeated in the file, with the difference or chosen row and whether the user confirmed it.
6. Prepare the import file. Use XML with field currencies for prices, XML for a PDF or section changes, and CSV for other flat data: use current catalog key values and only the values that change. A shared key can update every product with that value. Use it only if the user approved all those updates with the same source values. Otherwise choose an existing key that targets the selected product alone, or skip the row. Get separate approval for the final preview before writing. Before asking to add new products, verify the mapping of their names to the catalog column with the name role. Leave out unnamed new rows, report them as skipped, and ask about adding only the eligible rows (addNew). Never make up a value. Omit a missing price from the XML.

## matchReport

Every number of the side of the file is counted in rows of the file of the user, not in products of the catalog and not in rows of the prepared import file. Each row of the file of the user is in exactly one of exact, fuzzyConfirmed, fuzzySkipped, newRows, skippedRows, so they add up to sourceRows. Count unmatched rows eligible to add in newRows and rows that cannot be added for lack of a name in skippedRows. catalogOnly is counted in products of the catalog.

Example: the file of the user has 234 rows with a product; 150 have the key of a product (one of them gives its value to three products, 60 do not change the value: all count), 8 were matched by likeness and confirmed, 10 look alike and are not decided, 22 have no product in the catalog, 44 have no value or are discontinued: sourceRows 234, exact 150, fuzzyConfirmed 8, fuzzySkipped 10, newRows 22, skippedRows 44.

Always give two lists, `[]` when there are none:

- `oneRowManyProducts`: each row whose value goes to more than one product; the row, number of products, every difference found in the file and catalog data, and whether the user confirmed applying the row to all of them. Use an empty difference only when none was found; no kind of attribute is harmless by default. Several candidates still need confirmation when the difference is empty.
- `manyRowsOneKey`: each key that occurs in more than one row; the key, number of rows, which row was chosen for which product and why, and whether the user confirmed the choice.

Leave out unresolved, declined and unaddressable choices, including one source row for several products and repeated keys. Show why each affected row was left out and count those rows in `fuzzySkipped`. If the user already asked to skip a row, do not ask again. Preview the file again when the set of changes changes.
