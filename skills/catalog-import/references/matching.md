# Match a file with the catalog

For an update when the keys of the file are not exact, the source is a PDF or a messy Excel, there are several files, or a second supplier. These rules hold for any kind of goods. The snapshot of the catalog (get_catalog_snapshot) gives a short version in "guide"; this is the whole method.

1. Read the whole source (every sheet, every page). Make one table: a row is a future product. Leave out the titles of sections, the totals, the empty rows and columns; a title above a group is the section of the rows under it. A cell with several properties written together (a model, a size, a color) goes to several columns. A product with variants (a size, a color, a version) is a row for each variant, with its own name.
2. Tell the user how you understood the columns ("Item No. is the supplier article, Net dealer price is the purchase price") and the rules they gave. A column that was renamed since the last load and has the same data is the same column: use the column of the catalog, never make a new one.
3. Match the rows with this snapshot with a script on the CSV, not by reading it in the chat. The snapshot has the names of the columns, not their roles: read the roles with get_catalog (role vendorCode is the code of the product, name — the name, description and longDescription — the texts). Go down: the exact value of the code (the column with the role vendorCode); the same value without case, spaces, dashes and look-alike Cyrillic and Latin letters; then the name, then the texts, then any other columns that the file and the catalog both have.
   - Before you call a pair sure, compare every attribute the row states with the same attribute of the product, wherever it stands (the name, the texts, any column: a size, a volume, a power, a material, a version, a set, a pack): an attribute that the row states and the product contradicts makes the pair doubtful. A name, a color or a mark of a variant does not tell it.
   - Several products of the catalog may take the value of one row only if they differ by an attribute that the file does not state and the user said that this attribute does not change the value; otherwise ask, once for an attribute and not for each product.
   - When several rows of the file have the same key, the key does not choose the row: compare every attribute that each row states with each product, and the product goes to the row that fits it; no row fits clearly — that is a question.
   - If no column of the catalog has unique values, offer the user to add one for the code of the catalog (create_field, named in the language of the user), fill it once, and match by it the next time.
4. A pair found by likeness is never taken by yourself. Show the pairs in two groups, "sure" and "doubtful", each with the row of the file, the product, what is the same and what differs, and wait for the user. Ask in as few questions as you can: products that take the value of one row, or differ only by an attribute that the user said does not matter, are one question; a row with an exact key is no question at all. Use a threshold ("show me everything below 90%") only when the user named it; a percent is your estimate, not a measure.
5. Before preview_import tell the user in simple words: which products change and from what to what (all of them for a short file, examples for a long one); how many rows matched by the exact key, by likeness (confirmed, not confirmed), how many are new, how many are skipped and why, the duplicates inside the file, the products of the catalog that are not in the file; and the problems of the file with an offer ("rows 384–400 have no currency, the others look like USD: apply USD?"), never an error text. Give the user the CSV of the pairs (the row of the file, the product, how it was matched, what was decided, and the number of the question: the same for the products of one question). The same numbers go to matchReport of preview_import, counted in rows of the file of the user: its fields say how.
6. Make the CSV for the import (a YML instead, when the products must go to sections: see sections of preview_import): the key column with the value of the catalog (for a pair by likeness, the key of the product of the catalog, not of the file) and only the columns that change. Do not add products unless the user asked (addNew), and a row without a name is never added (leave it out of the CSV, count it as skipped). Never make up a value: an empty cell stays empty.

## matchReport

Every number of the side of the file is counted in rows of the file of the user, not in products of the catalog and not in rows of the CSV for the import. Each row of the file of the user is in exactly one of exact, fuzzyConfirmed, fuzzySkipped, newRows, skippedRows, so they add up to sourceRows. catalogOnly is counted in products of the catalog.

Example: the file of the user has 234 rows with a product; 150 have the key of a product (one of them gives its price to three colours, 60 do not change the price: all count), 8 were matched by likeness and confirmed, 10 look alike and are not decided, 22 have no product in the catalog, 44 have no price or are discontinued: sourceRows 234, exact 150, fuzzyConfirmed 8, fuzzySkipped 10, newRows 22, skippedRows 44.
